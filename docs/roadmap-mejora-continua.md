# Mejora continua: de tablero a asistente DMAIC

Especificacion de lo que falta construir. Escrito el 2026-08-06.

## Donde estamos

Hoy `mejora-continua.html` es un **tablero de seguimiento**: registra un
problema, sugiere el desperdicio Lean por palabras clave, lo mueve por las
fases DMAIC y no deja cerrar sin causa raiz ni accion de control.

Eso es un registro, no un asistente. Falta lo que convierte esto en una
herramienta Six Sigma de verdad: que **guie** al usuario por cada fase
exigiendo entregables, que **calcule** capacidad y estabilidad del proceso a
partir de datos reales, y que **exporte** el proyecto como informe.

Ademas hoy esta embebido con un iframe. **Tiene que ser nativo** (ver
`ARQUITECTURA.md`, seccion 6).

## 1. Modelo de datos

Lo actual no alcanza: `mejora_continua` es una tabla plana de campos de texto.
Sin datos crudos no hay Cp/Cpk ni grafico de control.

### `mc_charter` — Project Charter (1 a 1 con el caso)

```sql
create table public.mc_charter (
  id bigint generated by default as identity primary key,
  caso_id bigint not null unique references public.mejora_continua(id) on delete cascade,
  problema text,                    -- que pasa, donde, desde cuando, magnitud
  alcance_incluye text,
  alcance_excluye text,             -- tan importante como lo que incluye
  meta_smart text,                  -- "reducir X de 12% a 5% antes del 30/09"
  metrica_primaria text,
  linea_base numeric,
  objetivo numeric,
  unidad text,
  caso_negocio text,                -- impacto en dinero, riesgo o servicio
  patrocinador text,
  lider text,
  equipo text,
  fecha_inicio date,
  fecha_objetivo date,
  restricciones text,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```

### `mc_mediciones` — datos crudos

Sin esto no hay estadistica. Un renglon por muestra.

```sql
create table public.mc_mediciones (
  id bigint generated by default as identity primary key,
  caso_id bigint not null references public.mejora_continua(id) on delete cascade,
  momento text not null default 'antes' check (momento in ('antes','despues')),
  subgrupo integer,                 -- null = observaciones individuales (I-MR)
  valor numeric not null,
  medido_en timestamptz default now(),
  nota text
);
create index on public.mc_mediciones(caso_id, momento, medido_en);
```

`momento` permite comparar antes y despues y calcular la mejora real.

### `mc_especificacion` — limites del cliente

```sql
create table public.mc_especificacion (
  caso_id bigint primary key references public.mejora_continua(id) on delete cascade,
  lie numeric,      -- limite inferior de especificacion (LSL)
  lse numeric,      -- limite superior (USL)
  objetivo numeric,
  unidad text,
  tamano_subgrupo integer default 1
);
```

Ojo: LIE y LSE los define **el cliente o la norma**, nunca se calculan desde
los datos. Confundirlos con los limites de control es el error clasico.

### `mc_entregables` — el gating

```sql
create table public.mc_entregables (
  id bigint generated by default as identity primary key,
  caso_id bigint not null references public.mejora_continua(id) on delete cascade,
  fase text not null check (fase in ('Definir','Medir','Analizar','Mejorar','Controlar')),
  clave text not null,              -- 'charter', 'mapa_proceso', 'r&r', ...
  completado boolean not null default false,
  obligatorio boolean not null default true,
  contenido text,
  completado_en timestamptz,
  unique (caso_id, clave)
);
```

Los entregables minimos por fase, como semilla en `config_listas`:

| Fase | Entregables obligatorios |
| --- | --- |
| Definir | Charter, alcance, metrica primaria con linea base, SIPOC |
| Medir | Plan de recoleccion, datos cargados (n>=25), capacidad inicial |
| Analizar | Causa raiz con metodo declarado, evidencia (Pareto o hipotesis) |
| Mejorar | Acciones definidas, piloto, medicion posterior |
| Controlar | Plan de control, grafico de control, responsable, capacidad final |

Regla: no se avanza de fase si queda un entregable obligatorio sin completar.
Hoy existe una version blanda de esto (causa raiz para Mejorar, accion de
control para Cerrar); la nueva la generaliza.

### `mc_adjuntos`

Evidencia por caso y fase. Usar Supabase Storage, guardando aca la ruta.

**RLS**: mismo patron que el resto (`select` abierto a autenticados,
escritura con `puede_editar()`, borrado solo admin). Todas necesitan trigger
de `registrar_historial()`. Ver el checklist en `supabase/README.md`.

## 2. Calculadoras (JavaScript en el cliente)

Aritmetica directa. Lo importante es no equivocarse en las definiciones.

```
media       x̄ = Σx / n
sigma larga s = √( Σ(x - x̄)² / (n-1) )          -- desviacion muestral
sigma corta σ̂ = R̄ / d2      (subgrupos)
            σ̂ = MR̄ / 1.128  (individuales, d2 con n=2)
```

**Capacidad** (usa sigma corta, "lo que el proceso podria dar"):

```
Cp  = (LSE - LIE) / (6 σ̂)
Cpk = min( (LSE - x̄) / (3 σ̂), (x̄ - LIE) / (3 σ̂) )
```

**Desempeno** (usa sigma larga, "lo que el proceso realmente dio"):

```
Pp  = (LSE - LIE) / (6 s)
Ppk = min( (LSE - x̄) / (3 s), (x̄ - LIE) / (3 s) )
```

Con especificacion unilateral solo se calcula el lado que existe.

**Nivel sigma**:

```
DPMO  = (defectos / (unidades × oportunidades)) × 1 000 000
Zbench = normsinv(1 - DPMO/1e6)
nivel sigma ≈ Zbench + 1.5      -- el clasico corrimiento de 1.5σ
```

Interpretacion: Cpk < 1.0 incapaz; 1.0–1.33 marginal; 1.33–1.67 aceptable;
> 1.67 bueno. **Un Cp alto con Cpk bajo significa proceso descentrado**, no
proceso malo: se corrige moviendo la media, no reduciendo variacion.

**Advertencia obligatoria en la UI**: capacidad sobre un proceso inestable no
significa nada. Si el grafico de control muestra puntos fuera de limites, hay
que decirlo antes de mostrar el Cpk.

## 3. Graficos de control

### Constantes por tamano de subgrupo

| n | d2 | A2 | D3 | D4 |
| --- | --- | --- | --- | --- |
| 2 | 1.128 | 1.880 | 0 | 3.267 |
| 3 | 1.693 | 1.023 | 0 | 2.574 |
| 4 | 2.059 | 0.729 | 0 | 2.282 |
| 5 | 2.326 | 0.577 | 0 | 2.114 |
| 6 | 2.534 | 0.483 | 0 | 2.004 |
| 7 | 2.704 | 0.419 | 0.076 | 1.924 |
| 8 | 2.847 | 0.373 | 0.136 | 1.864 |

**I-MR** (individuales, n=1):
```
LC  = x̄                    LC_MR  = MR̄
LSC = x̄ + 2.66 MR̄          LSC_MR = 3.267 MR̄
LIC = x̄ - 2.66 MR̄          LIC_MR = 0
```

**X̄-R** (subgrupos):
```
LSC = x̄̄ + A2 R̄     LIC = x̄̄ - A2 R̄
LSC_R = D4 R̄        LIC_R = D3 R̄
```

### Reglas de Nelson (deteccion de senales)

Implementar como minimo las cuatro primeras:

1. Un punto a mas de 3σ de la linea central
2. Nueve puntos seguidos del mismo lado de la linea central
3. Seis puntos seguidos subiendo o bajando
4. Catorce puntos alternando arriba/abajo

Marcar el punto y decir que regla se violo.

### Otros graficos utiles

- **Pareto** de causas: ordena y acumula, marca el 80%
- **Histograma** con LIE/LSE superpuestos: muestra visualmente el descentrado
- **Antes/despues**: dos series, para evidenciar la mejora

Sin librerias pesadas: son SVG dibujados a mano, que es lo que ya hace la app
en el resto de los modulos.

## 4. Exportacion

**Recomendacion fuerte: `window.print()` con una hoja de estilos de impresion**,
no una libreria de PDF.

Motivos: peso cero (jsPDF + html2canvas son ~300 KB), la calidad de texto es
mejor porque no rasteriza, el usuario elige "Guardar como PDF" desde el dialogo
del navegador, y **la app ya tiene atributos `data-noprint` en el markup** — o
sea que el diseno original ya contemplaba imprimir.

Formatos a producir:

- **Informe DMAIC completo**: portada con el charter, una seccion por fase con
  sus entregables, graficos y tabla de capacidad, y cierre con el plan de
  control
- **A3**: una sola hoja apaisada en la grilla clasica — izquierda:
  contexto / situacion actual / analisis; derecha: objetivo / contramedidas /
  plan / seguimiento. Es un ejercicio de sintesis, no de volcar todo
- **Resumen ejecutivo**: una pagina con problema, meta, resultado y proximo paso

La consulta a Supabase junta `mejora_continua` + `mc_charter` +
`mc_especificacion` + `mc_mediciones` + `mc_entregables` y arma el documento en
el cliente.

## 5. Orden sugerido

Cada etapa se publica y verifica por separado.

1. **Modelo de datos**: migraciones, RLS, semilla de entregables por fase,
   prueba con cuenta lector
2. **Nativo**: sacar el iframe y escribir la vista dentro del bundle, con el
   asistente por fases y el gating. Es la etapa mas cara: hay que escribir el
   markup en el lenguaje de plantillas
3. **Charter**: formulario completo, como primer entregable de Definir
4. **Mediciones y calculadoras**: carga de datos (manual y CSV, que la app ya
   sabe hacer), Cp/Cpk/Pp/Ppk, nivel sigma
5. **Graficos**: I-MR, X̄-R, reglas de Nelson, Pareto, histograma
6. **Exportacion**: hoja de impresion, informe DMAIC, A3, resumen
7. **Integracion**: boton "enviar a evaluacion" desde las fichas de portafolio,
   tareas, radar y visitas, que crea el caso ya vinculado al registro de origen
   (agregar columnas `origen_tabla` y `origen_codigo`)

Si antes se hace la migracion a Vite (`migracion-vite.md`), conviene reordenar:
hacer la migracion primero y despues los puntos 2 en adelante, para no escribir
dos veces la misma vista.
